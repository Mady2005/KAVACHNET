# KAVACHNET
### AI-Based Cyber-Resilient Edge Intelligence for Remote Critical Operations

KAVACHNET is a modular AI-powered platform designed to support **secure, intelligent, and resilient operations in remote environments**, especially where network connectivity may be unreliable and continuous monitoring is important.

The project brings together three capabilities: **AI Security & Cyber Defense, Edge AI & Situational Intelligence, and Network Resilience & Real-Time Communication**. A shared decision engine is intended to combine information from these modules and recommend appropriate responses to security threats, equipment anomalies, and network disruptions.

> **Project status:** Phase 1 — Shared application foundation. The authentication, backend, database, and integration contracts establish the foundation for the three modules. Individual module capabilities are developed and integrated incrementally.

## 1. Problem Statement

Remote critical operations may face several challenges:

- **Cybersecurity threats:** Malicious prompts, unsafe documents, and attempts to manipulate AI systems can compromise the reliability of information.
- **Limited situational awareness:** Equipment and environmental sensor readings may indicate abnormal conditions that need timely investigation.
- **Unreliable connectivity:** Network degradation or temporary disconnections can interrupt communication and delay important messages.
- **Disconnected monitoring systems:** Security alerts, equipment events, and network conditions may need to be considered together rather than analyzed independently.

These challenges motivate a unified platform that can process events locally, identify potential risks, and adapt its communication behavior to changing conditions.

## 2. Our Solution

KAVACHNET combines three specialized modules through a common application backend and a centralized decision-making layer.

The platform is designed to:

- Detect and assess suspicious AI inputs.
- Analyze simulated sensor data for abnormal equipment behavior.
- Monitor network health and simulate connectivity failures.
- Prioritize important events and preserve messages during disconnections.
- Correlate events from different modules to provide a clearer operational picture.
- Present alerts, event histories, and system status through a unified dashboard.

The initial implementation uses simulated telemetry and controlled test scenarios. Real-world deployment would require further validation, security testing, and integration with authorized operational systems.

### Main components

- **Frontend:** Provides the interface for users to inspect events, alerts, and module status.
- **Backend API:** Handles authentication, authorization, event processing, and communication between application components.
- **Security module:** Evaluates suspicious inputs and generates security-related events.
- **Edge AI module:** Analyzes sensor observations and retrieves information from local documents.
- **Network module:** Evaluates simulated network conditions and manages message delivery during interruptions.
- **Decision engine:** Applies shared policies to module outputs and determines suitable responses.
- **Database:** Persists application records, events, and audit information.

### Shared event contract

All modules should use the shared `KavachEvent` schema rather than inventing incompatible event formats.

The contract provides a consistent way to represent information such as event type, severity, source, timestamp, and relevant scores. The exact fields and validation rules are defined in the backend schema.

This allows the modules to be developed independently while remaining compatible with the central application.

## 5. Three Core Modules

### Module 1 — AI Security & Cyber Defense

**Objective:** Identify potentially malicious inputs and reduce the risk of unsafe AI interactions.

Planned capabilities:

- Prompt-injection detection.
- Jailbreak-attempt classification.
- Malicious-document scanning.
- Policy-based input and output checks.
- Security event logging and alert generation.
- A security monitoring interface.

**Proposed approach:** Start with a TF-IDF and Logistic Regression classifier as a lightweight baseline. Evaluate transformer-based models such as MiniLM or DistilBERT as optional improvements.

**Expected output:** A structured security event containing the detection result, risk score, severity, and supporting evidence where available.

### Module 2 — Edge AI & Situational Intelligence

**Objective:** Analyze local data and sensor observations to identify unusual conditions and support decision-making when connectivity is limited.

Planned capabilities:

- Simulated temperature, humidity, vibration, power, and battery telemetry.
- Sensor anomaly detection.
- Local document search and retrieval-augmented generation (RAG).
- Optional local language-model inference through Ollama.
- Event correlation across sensor readings and time windows.
- Evidence-backed summaries of detected conditions.

**Proposed approach:** Use rule-based checks and Isolation Forest as initial anomaly-detection methods. Add a local embedding and retrieval pipeline for document intelligence.

**Expected output:** An event or summary that identifies an unusual observation, its supporting measurements, and the relevant source information.

### Module 3 — Network Resilience & Real-Time Communication

**Objective:** Maintain reliable message handling when connectivity deteriorates or becomes temporarily unavailable.

Planned capabilities:

- Network-health monitoring and scoring.
- A controlled network-degradation simulator.
- Message priority levels: P0, P1, P2, and P3.
- Compression using gzip or zlib.
- Persistent offline message storage.
- Retry and recovery workflows.
- Real-time updates using FastAPI WebSockets.
- Communication analytics and delivery metrics.

**Proposed approach:** Use simulated network telemetry, a persistent SQLite outbox, priority-based message handling, and controlled retry/backoff logic.

**Expected output:** A record of message priority, delivery status, queue time, compression results, and recovery behavior.

## 6. How KAVACHNET Works

The intended end-to-end workflow is:

1. **Collect:** Receive an input, sensor observation, or communication-status update.
2. **Analyze:** The relevant module evaluates the input and identifies potential risks or anomalies.
3. **Generate an event:** The module produces a structured event using the shared schema.
4. **Evaluate context:** The decision engine considers event severity, security risk, and network health.
5. **Choose a response:** The platform applies an appropriate policy, such as warning, blocking, alerting, prioritizing, or storing a message.
6. **Persist and communicate:** Events are recorded, and eligible messages are delivered or queued according to network conditions.
7. **Display:** The dashboard presents the event, status, and available evidence to the user.

### Example demonstration scenario

Consider a simulated remote monitoring environment:

- A user submits a suspicious instruction to an AI-powered document assistant.
- The security module flags the input and creates a security event.
- A simulated sensor stream reports an unusual vibration pattern.
- The edge module detects the anomaly and generates an equipment alert.
- The network simulator introduces a temporary connectivity disruption.
- The communication module queues messages and prioritizes critical alerts.
- When connectivity is restored, queued messages are processed according to the delivery policy.
- The dashboard displays the resulting events and communication status.

This demonstration tests how the modules interact. It does not imply that every capability is already implemented or that the system is ready for deployment in operational environments.

## 9. Getting Started

### Prerequisites

Install the following software:

- Python 3.11 or later.
- Node.js 20 or later and npm.
- Git.

Docker, cloud services, external AI APIs, and external datasets are not required for the shared Phase 1 foundation.

### Step 1 — Clone the repository

```bash
git clone <YOUR_GITHUB_REPOSITORY_URL>
cd KAVACHNET
```

Replace the placeholder with your repository's actual URL.

### Step 2 — Configure the environment

Run the following commands in PowerShell from the repository root:

```powershell
Copy-Item .env.example .env
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
```

### Step 3 — Initialize the database

```powershell
Set-Location backend
alembic upgrade head
Set-Location ..
```

### Step 4 — Provision development users

```powershell
python scripts\provision_dev_users.py
```

Follow the prompts to set or generate development passwords. Generated passwords should be stored securely. This command is intended for local development.

### Step 5 — Start the backend

Open a terminal in the repository root:

```powershell
.\.venv\Scripts\Activate.ps1
Set-Location backend
uvicorn app.main:app --reload
```

The API should be available at:

`http://127.0.0.1:8000`

### Step 6 — Start the frontend

Open a second terminal in the repository root:

```powershell
Set-Location frontend
npm install
npm run dev
```

Open the local frontend address shown by Vite, typically:

`http://127.0.0.1:5173`

Log in using the development account created during provisioning.

**Important:** These instructions assume the corresponding files and scripts exist in your checked-out repository. Follow the actual repository configuration if it has changed.

## 10. Configuration

Copy `.env.example` to `.env` before running the application.

Review the configuration for:

- Application environment.
- Database connection.
- JWT signing secret and token expiration.
- Cookie security settings.
- Frontend and backend URLs.
- Registration and account-provisioning controls.

For deployment beyond local development:

- Generate a strong, unique signing secret.
- Use HTTPS and secure cookie settings.
- Keep credentials out of source control.
- Restrict account provisioning and registration.
- Apply role-based authorization to protected operations.
- Review logging, retention, and access-control policies.

Never commit `.env` files, passwords, tokens, or sensitive operational data.

## 14. Security and Limitations

KAVACHNET is a prototype and research-oriented engineering project. Its intended use is to demonstrate modular security analysis, edge intelligence, and resilient communication.

Current design considerations:

- Simulated sensor and network data should be clearly distinguished from real measurements.
- Machine-learning detections are probabilistic and can produce false positives or false negatives.
- Local inference and offline workflows require validation on the target hardware.
- Authentication and authorization do not, by themselves, establish production readiness.
- Network recovery and message prioritization require tests for duplicate delivery, stale events, persistence, and failure handling.
- AI-generated summaries must be traceable to available evidence and should not be treated as independently verified facts.

**No real military operational data, credentials, classified information, or sensitive infrastructure details should be committed to this repository.** Use synthetic data and authorized test environments.
